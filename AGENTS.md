# Контекст проекта для Codex

## Как пользоваться этим файлом

Прочитай этот файл при начале работы. Он сохраняет договорённости между чатами,
но не заменяет проверку текущего кода. Перед изменениями проверь ветку, `git status`
и относящиеся к задаче файлы. Не перечитывай весь репозиторий без необходимости.
Указания пользователя в текущем чате имеют приоритет. Обновляй этот файл при
изменении важных договорённостей; не записывай сюда секреты и временные логи.

## Проект и структура

- OnlySeans — учебный аналог Кинопоиска: фильмы, персоны, оценки, рецензии,
  пользовательские библиотеки и авторизация.
- Backend на Go. Модуль: `github.com/go-park-mail-ru/2026_2_OnlySeans`.
  Версию Go и зависимости проверяй в `go.mod`.
- Архитектура — монолит с разделением на слои:
  - `internal/domain`: модели предметной области, ошибки и интерфейсы репозиториев.
  - `internal/usecase`: сценарии приложения и их входные/выходные DTO.
  - `internal/delivery`: HTTP-обработчики, преобразование запросов и ответов.
  - `internal/delivery/router`: маршрутизация Gorilla Mux и middleware.
  - `internal/services`: реализации репозиториев и прикладных сервисов.
  - `internal/storage`: подключение PostgreSQL и работа с объектным хранилищем.
  - `internal/app`: сборка зависимостей и запуск приложения.
  - `internal/config`, `configs`: конфигурация.
  - `pkg/logger`, `pkg/redis`: общие компоненты.
- Точка входа: `cmd/main.go`. Контракт HTTP API: `documentation.yaml`.
- SQL-миграции: `db/migrations`, последовательное применение: `db/apply_all.sql`.
  Описание БД: `db/README.md`, `db/normalized`.
- Тесты преимущественно находятся в `tests`, по областям приложения.
- В `docker-compose.yaml` описаны backend, PostgreSQL, Redis и RustFS
  (S3-совместимое хранилище). Актуальные версии и порты смотри в Compose.

## Предпочтения пользователя и правила изменений

- Общайся по-русски. Пользователь изучает backend: объясняй назначение решений
  простыми словами, связывая примеры с проектом.
- Если пользователь просит теорию или пример в чате и запрещает создавать файлы,
  не изменяй проект. При просьбе исправить или реализовать — выполни работу.
- После изменений кратко объясни, что изменилось, зачем и как проверялось.
- Не меняй несвязанные области, особенно рецензии, ради общей чистки или
  форматирования. Сохраняй существующие пользовательские изменения.
- У каждого usecase свои DTO в слое usecase; не переноси такие DTO в domain.
- Для поиска пользователь явно выбрал: конструктор input возвращает указатель,
  а метод `Run` принимает input по значению. Не меняй это без причины.
- HTTP-проверки формата параметров относятся к delivery; бизнес-инварианты
  должны проверяться и при вызове usecase без HTTP.
- Используй существующий `logger.Logger` и помощники
  `internal/usecase/logging`, где они подходят. Не дублируй одну ошибку в логах
  каждого слоя; клиенту не возвращай внутренние тексты ошибок инфраструктуры.
- Сгенерированные файлы не редактируй вручную: меняй контракт/конфигурацию
  генератора, затем запускай генерацию, если она нужна для задачи.
- Сохраняй кодировку UTF-8. В PowerShell явно указывай её при чтении русского текста.
- `.42c/` — служебная папка расширения VS Code 42Crunch OpenAPI.
  Не считай её частью backend и не удаляй без запроса.

## Договорённости по поиску из предыдущих чатов

Это контекст разработки, а не утверждение о наличии реализации в текущей ветке.

- Для учебного проекта выбраны PostgreSQL и `pg_trgm`, поиск внутри монолита.
  Elasticsearch и Meilisearch обсуждались как альтернативы.
- Нужны поиск фильмов по русскому/оригинальному названию, поиск актёров и
  режиссёров, поддержка опечаток.
- Подсказки содержат две группы: фильмы и персоны. Отдельную группу
  «фильмы с найденным человеком» пользователь решил убрать.
- Обсуждавшийся контракт: `GET /api/search/suggest`, операция
  `getSearchSuggestions`; `q` после обрезки пробелов — 2–200 Unicode-символов;
  `limit` — 1–5, по умолчанию 3, отдельно для каждой группы.
- Пустые списки в JSON должны быть `[]`, ошибки — в согласованном JSON-формате.
  Ошибки разбора параметров сгенерированной обвязкой также требуют обработки.
- Для HTTP-обвязки использовался oapi-codegen: модели, Gorilla server и strict
  server; размещение в `internal/delivery/search` устраивает пользователя.
- На момент создания этого файла, 21.11.2026, активна ветка `dev`; в ней нет
  файлов поиска, `oapi-codegen.yaml` и `.golangci.yml` из предыдущей работы.
  Не восстанавливай их автоматически и не переноси изменения между ветками
  без задачи пользователя. Сначала проверь состояние нужной ветки.

## Обсуждение метрик и мониторинга

- Пользователь планирует Prometheus и Grafana; пока просил объяснить теорию.
  Само обсуждение не является поручением внедрить мониторинг.
- Обсуждались три группы метрик: бизнес-действия, HTTP API, ресурсы.
- Успешные оценки/рецензии считаются на backend после сохранения; HTTP-метрики
  собираются middleware; ресурсы — коллекторами и экспортёрами.
- Для клиентских действий обсуждалась общая ручка приёма событий, например
  `POST /api/analytics/events`. Это предложение, не готовый контракт.
- Не подменяй число запросов подсказок числом поисковых сессий.
- Не используй ID пользователей, текст поиска и другие неограниченные значения
  как labels Prometheus. Для URL используй шаблон маршрута.
- Точные события, уникальные пользователи и воронки требуют отдельного хранения;
  счётчики Prometheus не заменяют данные PostgreSQL.
- В схеме БД уже описана область аналитики (`visitor`, `visit`, `analytic_event`,
  `search_query` и другие таблицы). Перед новой реализацией проверь миграции
  и наличие кода, чтобы не создать дублирующую модель.

## Проверка изменений

- Форматируй изменённые Go-файлы через `gofmt`.
- Запускай относящиеся к изменению тесты: `go test ./tests/<область>`
  и при необходимости тесты затронутых пакетов.
- Для широкой проверки доступны `go test ./...` и `go vet ./...`.
  Команды запуска приложения и генерации сверяй с текущим `Makefile`
  и `generate.go`.
- Если в текущей ветке есть `.golangci.yml`, используй её и совместимую версию
  golangci-lint. Не считай старые результаты линтера актуальными для другой ветки.
- Не исправляй все старые замечания проекта в рамках небольшой задачи.
  Отделяй проблемы изменённого кода от существовавших ранее.
- Для интеграционных тестов нужна соответствующая инфраструктура. Пропущенный
  тест и тест с mock не подтверждают работу SQL на живой БД.
- Не запускай миграции на пользовательской БД и не удаляй Docker volumes
  только ради проверки кода без соответствующего поручения.
- Если проверки не запускались или недоступны, прямо укажи это в результате.
